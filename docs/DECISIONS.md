## ADR-0001：不使用 LangGraph（也不使用任何 agent 框架）

**状态**：已接受（2026-11-17）
**决策**：编排层用普通的 Python 显式状态机，不引入 LangGraph / LangChain。

### 背景

问数系统的编排确实涉及多步、有分支、有重试、有人工澄清。
LangGraph 正好覆盖这些概念（graph / state / checkpointer / interrupt），
所以"要不要用"是个真问题，不是随手能打发的。

### 决策理由

**1. LangGraph 的核心卖点是"图由模型动态决定"，而本项目的设计恰好相反。**

LangGraph 适合的是 agent 自主规划：模型决定下一步走哪个节点。
本项目刻意**把选择边的权力从模型手里拿走**——分诊五分类、槽位检查、
编译器、校验器都是确定性的。用 LangGraph 等于为一个你不用的能力付依赖成本。

**2. 我们唯一真正重叠的能力是 human-in-the-loop，但它跨请求。**

LangGraph 的 `interrupt` 适合"进程内暂停等人"。
而问数的澄清是**跨 HTTP 请求**的：这一轮返回问题，下一轮用户回答，
中间可能是几分钟到几天。我们已经在数据库里持久化了
`question_execution_record`（含结构化结果、answer_path、status）。
LangGraph 的 checkpointer 会变成第二套状态存储，且序列化到 Postgres 更复杂。

**3. LangChain 生态的版本波动成本，在银行这种长周期项目里被放大。**

需要三五年维护的系统，依赖越少越好。当前 `requirements.txt` 只有 16 个包，
没有一个是框架。这个状态值得保护。

**4. 我们需要的状态机很小。**

状态数 ≤ 6（分诊 / 理解 / 检索 / 编译 / 执行 / 澄清），带一个重试预算和一个追问预算。
纯 Python 写出来约 200 行，可以被 100% 单测覆盖，打日志也直白。

### 什么情况下翻案

* 需要**进程内**长时间暂停（例如生成 SQL 前需要人工审批，且必须保持数据库连接）
* 需要**动态图**：模型真的要根据中间结果决定走哪条分析路径（例如开放式归因分析，
  路径数量不可枚举）
* 出现需要并行 fan-out 到几十个子任务且结果要合并的场景

以上任一成立时，重开这条决策。**迁移成本很低**，因为
`app/engine/{validation,clarify}` 都是纯函数（输入 SQL/Intent，输出问题清单），
不含任何框架类型。这是刻意的：**引擎层不认识框架，框架才可能被替换。**

### 顺带说明：面试相关性

市场上 LangGraph 是高频关键词。但这不构成在**产品代码**里引入它的理由。
想积累 LangGraph 经验，用一个独立的小项目更合适——
在产品里为了简历引入框架，长期成本由团队承担。

## ADR-0002：检索用「混合召回 + 重排」，但不用向量距离判"能不能答"

**状态**：已接受，实现细节待 Step 2 校准
**决策**：

1. **要** embedding 模型——用于**概念级召回**（哪个指标 / 哪个维度 / 哪张表）
2. **不要**用 embedding 做**值级映射**（机构号、码值、产品编码）——必须精确匹配
3. **要**重排模型——但只在候选数 > 阈值时启用，且用 cross-encoder，不用 LLM 打分
4. **不要**用向量距离阈值判断"可答 / 不可答"——那个判据在审计上站不住

### 为什么概念级要用 embedding

银行问数最大的问题是**词汇不匹配**：

```
用户说："不良贷款"        → 语义层是：fiv_lev_cla_flag IN ('30','40','50')
用户说："渝北支行"        → 语义层是：org_no = 'B001'
用户说："核销了多少"      → 指标是：writeoff_balance（默认口径）
```

askdb 的解法是 `synonym_dict` + `code_mapping` + 相似问库——**人工枚举**。
这在长尾上必然覆盖不住（这正是它准确率上限的来源之一）。
embedding 解决的是"口语 → 概念"的长尾召回。

### 为什么值级绝不能用 embedding

embedding 对**编码和数字**几乎无效，而且错得很难发现：

* `B001` 和 `B002` 在向量空间里可能非常接近（同构字符串）
* `LP03` 和 `LP04` 可能比 `LP03` 和"小微企业贷款"更近
* 机构号、产品码、科目号这类标识符，**语义相似 ≠ 业务等价**

值级映射只能靠三样东西，且优先级从高到低：

1. **精确等值**（数据库里真实存的值）
2. **别名表**（配置的标准化全称 / 简称）
3. **高枚举 KB**（TopK 候选也必须做等值确认，不能直接用）

这条对应规则 `R-ORG-001`（待实现）：网点名称必须等值匹配，禁止 LIKE / 前缀 / 包含。

### 为什么不用向量距离判"可答"

auto-ontology 的 `check_answerable` 用 `coverage = 命中实体 / 总实体`，
其中"命中"= 距离小于阈值。这个阈值在银行审计场景里无法解释：

* 为什么是 0.35 而不是 0.40？
* 换一个 embedding 模型，阈值全部失效
* 距离 0.36 的问题被判"不可答"，但它真的不可答吗？

**替代判据（本项目采用）**：可答性由**语义层的显式存在性**决定

```
问题实体 → 在语义层里找对应条目
  指标存在吗？（指标字典里有这个指标或它的同义词）
  维度值存在吗？（码值表 / 别名表里有这个值）
  时间可解析吗？（时间口径表能解析）
```

这是可解释的、可审计的、换模型不失效的。向量检索只负责**把候选捞出来**，
不负责**做判定**。

### 为什么重排不用 LLM 打分

askdb 的 `rerank_score` 是**模型打的分**（阈值 0.7 → confidence 0.9/0.4）。问题：

* 每个问题多付一次 LLM 调用（延迟 + 成本）
* 分数不可复现（同一问题两次可能不同）
* 0.7 这个阈值是拍的，没有校准依据
* 分数直接决定 confidence，而 confidence 又影响下游行为 —— 一个不稳定的数字
  决定了业务行为

**替代方案**：cross-encoder 重排模型（如 `bge-reranker-v2-m3`），只做**排序**，
不做判定。候选 ≤ 5 时跳过重排。判定仍由精确匹配规则做。

### 需要什么模型

| 用途 | 要求 | 候选 |
|---|---|---|
| Embedding | **必须支持中文**，可私有部署（银行数据不能出域） | `bge-m3`、`bge-large-zh-v1.5`、`Qwen3-Embedding` |
| Rerank | 中文短查询效果好，可私有部署 | `bge-reranker-v2-m3` |

**必须私有部署**，这是银行的硬约束，不是偏好。

### 一个能省事的规模判断

先算一下量级：

```
语义层假设规模：200 张表 + 3000 个字段 + 150 个指标 ≈ 3300 个文档
向量维度 1024，float32
→ 3300 × 1024 × 4B ≈ 13.5 MB
```

**13.5 MB。暴力余弦相似度检索 3300 条，numpy 里是亚毫秒级。**

所以**一开始根本不需要向量数据库**（不需要 pgvector 的索引，不需要 Chroma，
不需要 Milvus）。把向量加载到内存里，用 numpy 做矩阵乘就行。

pgvector 已经装在 docker-compose 里，留着没问题（元数据也要存）；
但**不要因为"要做 RAG"就去搭向量库**——在这个规模上它是纯负担。
等语义层真的到了十万级文档再谈索引。

### 什么情况下翻案

* 语义层文档数超过 10 万 → 需要 ANN 索引（pgvector HNSW 或专用库）
* 中文领域词（银行内部黑话）embedding 召回明显失效 → 需要微调或换模型
  （这时用评测集量化，不要凭感觉）
* 精确匹配 + 别名表已经能覆盖 95% 的头部问题 → 可以推迟引入 embedding，
  先做规则，再补向量

最后这条尤其重要：**先在评测集上量出"纯规则能到多少"**，
再决定 embedding 值不值得引入。否则你不知道它带来了多少增益。
