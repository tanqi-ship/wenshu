## ADR-0001：不使用 LangGraph（也不使用任何 agent 框架）

**状态**：已接受（2026-11-17）
**决策**：编排层用普通的 Python 显式状态机，不引入 LangGraph / LangChain。

### 背景

问数系统的编排确实涉及多步、有分支、有重试、有人工澄清。
LangGraph 正好覆盖这些概念（graph / state / checkpointer / interrupt），
所以"要不要用"是个真问题，不是随手能打发的。

### 决策理由

**1. LangGraph 的核心卖点是"图由模型动态决定"，而本项目的设计恰好相反。**

LangGraph 适合的是 agent 自主规划：模型决定下一步走哪个节点。
本项目刻意**把选择边的权力从模型手里拿走**——分诊五分类、槽位检查、
编译器、校验器都是确定性的。用 LangGraph 等于为一个你不用的能力付依赖成本。

**2. 我们唯一真正重叠的能力是 human-in-the-loop，但它跨请求。**

LangGraph 的 `interrupt` 适合"进程内暂停等人"。
而问数的澄清是**跨 HTTP 请求**的：这一轮返回问题，下一轮用户回答，
中间可能是几分钟到几天。我们已经在数据库里持久化了
`question_execution_record`（含结构化结果、answer_path、status）。
LangGraph 的 checkpointer 会变成第二套状态存储，且序列化到 Postgres 更复杂。

**3. LangChain 生态的版本波动成本，在银行这种长周期项目里被放大。**

需要三五年维护的系统，依赖越少越好。当前 `requirements.txt` 只有 16 个包，
没有一个是框架。这个状态值得保护。

**4. 我们需要的状态机很小。**

状态数 ≤ 6（分诊 / 理解 / 检索 / 编译 / 执行 / 澄清），带一个重试预算和一个追问预算。
纯 Python 写出来约 200 行，可以被 100% 单测覆盖，打日志也直白。

### 什么情况下翻案

* 需要**进程内**长时间暂停（例如生成 SQL 前需要人工审批，且必须保持数据库连接）
* 需要**动态图**：模型真的要根据中间结果决定走哪条分析路径（例如开放式归因分析，
  路径数量不可枚举）
* 出现需要并行 fan-out 到几十个子任务且结果要合并的场景

以上任一成立时，重开这条决策。**迁移成本很低**，因为
`app/engine/{validation,clarify}` 都是纯函数（输入 SQL/Intent，输出问题清单），
不含任何框架类型。这是刻意的：**引擎层不认识框架，框架才可能被替换。**

### 顺带说明：面试相关性

市场上 LangGraph 是高频关键词。但这不构成在**产品代码**里引入它的理由。
想积累 LangGraph 经验，用一个独立的小项目更合适——
在产品里为了简历引入框架，长期成本由团队承担。

## ADR-0002：检索用「混合召回 + 重排」，但不用向量距离判"能不能答"

**状态**：已接受，实现细节待 Step 2 校准
**决策**：

1. **要** embedding 模型——用于**概念级召回**（哪个指标 / 哪个维度 / 哪张表）
2. **不要**用 embedding 做**值级映射**（机构号、码值、产品编码）——必须精确匹配
3. **要**重排模型——但只在候选数 > 阈值时启用，且用 cross-encoder，不用 LLM 打分
4. **不要**用向量距离阈值判断"可答 / 不可答"——那个判据在审计上站不住

### 为什么概念级要用 embedding

银行问数最大的问题是**词汇不匹配**：

```
用户说："不良贷款"        → 语义层是：fiv_lev_cla_flag IN ('30','40','50')
用户说："渝北支行"        → 语义层是：org_no = 'B001'
用户说："核销了多少"      → 指标是：writeoff_balance（默认口径）
```

askdb 的解法是 `synonym_dict` + `code_mapping` + 相似问库——**人工枚举**。
这在长尾上必然覆盖不住（这正是它准确率上限的来源之一）。
embedding 解决的是"口语 → 概念"的长尾召回。

### 为什么值级绝不能用 embedding

embedding 对**编码和数字**几乎无效，而且错得很难发现：

* `B001` 和 `B002` 在向量空间里可能非常接近（同构字符串）
* `LP03` 和 `LP04` 可能比 `LP03` 和"小微企业贷款"更近
* 机构号、产品码、科目号这类标识符，**语义相似 ≠ 业务等价**

值级映射只能靠三样东西，且优先级从高到低：

1. **精确等值**（数据库里真实存的值）
2. **别名表**（配置的标准化全称 / 简称）
3. **高枚举 KB**（TopK 候选也必须做等值确认，不能直接用）

这条对应规则 `R-ORG-001`（待实现）：网点名称必须等值匹配，禁止 LIKE / 前缀 / 包含。

### 为什么不用向量距离判"可答"

auto-ontology 的 `check_answerable` 用 `coverage = 命中实体 / 总实体`，
其中"命中"= 距离小于阈值。这个阈值在银行审计场景里无法解释：

* 为什么是 0.35 而不是 0.40？
* 换一个 embedding 模型，阈值全部失效
* 距离 0.36 的问题被判"不可答"，但它真的不可答吗？

**替代判据（本项目采用）**：可答性由**语义层的显式存在性**决定

```
问题实体 → 在语义层里找对应条目
  指标存在吗？（指标字典里有这个指标或它的同义词）
  维度值存在吗？（码值表 / 别名表里有这个值）
  时间可解析吗？（时间口径表能解析）
```

这是可解释的、可审计的、换模型不失效的。向量检索只负责**把候选捞出来**，
不负责**做判定**。

### 为什么重排不用 LLM 打分

askdb 的 `rerank_score` 是**模型打的分**（阈值 0.7 → confidence 0.9/0.4）。问题：

* 每个问题多付一次 LLM 调用（延迟 + 成本）
* 分数不可复现（同一问题两次可能不同）
* 0.7 这个阈值是拍的，没有校准依据
* 分数直接决定 confidence，而 confidence 又影响下游行为 —— 一个不稳定的数字
  决定了业务行为

**替代方案**：cross-encoder 重排模型（如 `bge-reranker-v2-m3`），只做**排序**，
不做判定。候选 ≤ 5 时跳过重排。判定仍由精确匹配规则做。

### 需要什么模型

| 用途 | 要求 | 候选 |
|---|---|---|
| Embedding | **必须支持中文**，可私有部署（银行数据不能出域） | `bge-m3`、`bge-large-zh-v1.5`、`Qwen3-Embedding` |
| Rerank | 中文短查询效果好，可私有部署 | `bge-reranker-v2-m3` |

**必须私有部署**，这是银行的硬约束，不是偏好。

### 一个能省事的规模判断

先算一下量级：

```
语义层假设规模：200 张表 + 3000 个字段 + 150 个指标 ≈ 3300 个文档
向量维度 1024，float32
→ 3300 × 1024 × 4B ≈ 13.5 MB
```

**13.5 MB。暴力余弦相似度检索 3300 条，numpy 里是亚毫秒级。**

所以**一开始根本不需要向量数据库**（不需要 pgvector 的索引，不需要 Chroma，
不需要 Milvus）。把向量加载到内存里，用 numpy 做矩阵乘就行。

pgvector 已经装在 docker-compose 里，留着没问题（元数据也要存）；
但**不要因为"要做 RAG"就去搭向量库**——在这个规模上它是纯负担。
等语义层真的到了十万级文档再谈索引。

### 什么情况下翻案

* 语义层文档数超过 10 万 → 需要 ANN 索引（pgvector HNSW 或专用库）
* 中文领域词（银行内部黑话）embedding 召回明显失效 → 需要微调或换模型
  （这时用评测集量化，不要凭感觉）
* 精确匹配 + 别名表已经能覆盖 95% 的头部问题 → 可以推迟引入 embedding，
  先做规则，再补向量

最后这条尤其重要：**先在评测集上量出"纯规则能到多少"**，
再决定 embedding 值不值得引入。否则你不知道它带来了多少增益。

## ADR-0003：不迁移 askdb，只做单条主链路

**状态**：已接受（推翻原 `MIGRATION.md` 的五步迁移计划）
**决策**：不复制、不迁移 askdb 的任何代码。本项目只实现一条链路：**问题 → Intent → 编译 → 校验 → 出数**，其余全部不做。

### 背景

原计划是"选择性搬入"：只搬横切能力（连接器 1,206 行、权限 636 行、派生指标 1,346 行、模型 960 行、前端 70 文件……合计约 19,400 行 + 70 个前端文件），把编排主干重写。

### 决策理由

**1. 参考项目在本机跑不起来，因此"迁移"无法验证。**

askdb 需要 MySQL（应用库）、Oracle/PostgreSQL（业务库）、千帆知识库凭证、LLM 端点。缺任一项，页面/接口就退化成空壳。搬进来的代码无法执行 = 只能读，不能验证。

**2. 要改的正是架构本身，而搬入的每一块都会成为阻力。**

搬进来的 `connector_manager.py` 会要求 `crud` 和 `models`；`models` 会要求 `db/database.py` 的 44 张表迁移；`api/` 会要求 `middleware/auth.py`。**这不是"搬一个文件"，是搬一棵依赖树。** 而这条依赖树与本项目要验证的东西（编译器是否更准）没有关系。

**3. 学习目标与迁移目标冲突。**

迁移的产出是"一个能替代旧系统的系统"；学习的产出是"能讲清每个取舍的判断"。前者要求覆盖度，后者要求深度。**覆盖面一上来就会吃掉全部时间预算。**

### 后果（明确接受）

| 失去 | 补偿 |
|---|---|
| 多数据源连接器（Oracle/MySQL/Trino） | 只做 SQLite + 可选 PostgreSQL（ADR-0006） |
| 三层权限的现成实现 | 重写为 `Scope` 对象（ADR-0004），约 100 行 |
| 前端 | 不做。引擎输出形态未定时写前端，改起来比写起来贵 |
| 双引擎对照门禁 | 改为**黄金集门禁**：新模式 vs `eval/golden/*.sql` 手工黄金 SQL |
| 真实业务数据 | 用 `fixtures/sql/bank_fixture.sql` + 故意的 D-01~D-11 缺陷 |

### 什么情况下翻案

* 需要把本项目用于**真实生产环境**（那时不是"迁移代码"，是"重新评估要不要买/自建"）
* 需要的某项能力（如 Oracle 方言、行级权限）在评测中被证明是瓶颈，且重写成本 > 搬运成本
* 出现"必须在 1 个月内跑通 20 张表"这类硬期限

### 附：askdb 的正确用法

作为**阅读标本**：`docs/REFERENCES.md` 是一份阅读地图，按"值得读 / 只读结论 / 不必读"分了三类，并把它的 8 处踩坑整理成设计检查表。**这比它的代码更有价值。**

## ADR-0004：权限做"输入"，不做"系统"

**状态**：已接受
**决策**：权限以一个 `Scope` 值对象作为编译器的第三个输入；**不做**用户表、角色表、登录、JWT、RBAC、审计日志。

### 背景

askdb 的权限做得扎实（表/列/行三层纵深），但代价是 44 张表 + 认证中间件 + 前端菜单。对本项目来说，这些东西和"问题→SQL"没有关系。

### 决策理由

**1. 权限在编译器架构里天然是一个参数，不是一套系统。**

```python
compile_intent(intent, semantic, scope) -> exp.Select
```

`Scope` 由调用方构造，引擎不查库。测试里直接构造一个 `Scope` 就能测权限行为，**不需要任何用户体系**。

**2. 因为 SQL 只在一处生成，权限就只在一处注入。**

askdb 的权限注入分散在多处，其 `AGENTS.md` 自承 "there have been leakage bugs here before"。编译器架构直接消除了这个类别的问题——这是"确定性生成"的附带收益。

**3. 三层纵深不是重复，是防不同类型的事故。**

| 位置 | 防什么 | 若缺失 |
|---|---|---|
| L2 检索前过滤候选表 | 模型看不到无权限的表 | 幻觉 / 越权尝试 |
| L3 编译时注入行级 WHERE | 数据天然受限 | 越权读数据 |
| L4 AST 白名单复核 | **编译器的 bug** | 编译器 bug 变成越权事故 |

第三层尤其不能省：编译器也会写错（见 M1 的风险清单），需要一层**不信任编译器**的独立检查。

### 两个必须遵守的约束

1. **业务过滤与权限过滤必须分开。** 两者都进 `WHERE`，但用户能看见/能改前者，绝不能看见/改后者。合成时最后才合并，合并后不允许下游修改权限部分。
   （askdb 用 `rebuild_sql_service.py:145` 的 `_authorized_rebuild_scope()` 打补丁解决这个问题；本项目在结构上直接避免。）
2. **`Scope` 缺失时必须 fail-closed**，不能退化为"无限制"。

### 什么情况下翻案

* 需要接入真实用户体系（那时做的是"从 `Scope` 适配到认证系统"，而不是反过来）
* 出现**列级**动态脱敏需求（当前 `Scope.columns` 只做可见/不可见，不做值变换）

## ADR-0005：编译器与校验器互相独立，且编译失败不重试

**状态**：已接受
**决策**：
1. 校验器只接收 **SQL 文本**，不接收编译器的任何中间产物。
2. 编译失败**不重试**——它是确定性的。

### 为什么校验器不能看编译器的中间结果

如果校验器复用编译器的 AST，那么编译器的 bug 会被"它自己的校验"放过。**独立才叫兜底。**

这条直接对应 ADR-0004 的第三层：即使 SQL 是编译器生成的，也必须重新 parse 成树再检查一遍。

### 为什么编译失败不重试

`compile(intent, semantic, scope)` 是纯函数：同样输入永远同样输出。重试 100 次还是同一个失败。

**唯一能改变结果的是改变输入**，而输入只有三个来源：

| 失败原因 | 改哪个输入 | 谁来做 |
|---|---|---|
| 覆盖不足（指标/维度不存在） | 改语义层 | 配置维护者 |
| 意图不完整（用户没说清） | 改 `Intent` | **回 L2 澄清，问用户** |
| 配置有 bug（类型不合法） | 改语义层 | 报错给维护者，**不降级不重试** |

因此"重试"这件事在本项目只可能出现在**长尾路径**（M4 之后，模型自由写 SQL 时的降级），永远不出现在编译路径。

### 什么情况下翻案

* 编译器里引入了外部不确定性（例如公式涉及 LLM 生成）——那时它就不再是编译器了，应先解决那个不确定性
* 出现"编译失败但只差一点点，自动修补一下就能过"的可靠模式——即便那时也应该是**确定的修复规则**，不是重试

## ADR-0006：fixture 数据库默认用 SQLite，PostgreSQL 可选

**状态**：已接受（调整 M0 的 docker-compose 默认值）
**决策**：默认 fixture 用 SQLite（文件或内存）；PostgreSQL 只在需要方言 / EXPLAIN 验证时通过 `WENSHU_FIXTURE_URL` 启用。

### 决策理由

**1. "零依赖可跑"是本项目的关键目标。**

CI 里跑一个 pgvector service 意味着：本地开发要装 Docker、CI 要等容器健康检查、任何环境问题都会表现为测试失败。而 M1~M3 的全部工作（编译器 + 校验 + 澄清）都是**纯内存**的——它们只需要 `sqlglot`，不需要任何数据库。

**2. ADR-0002 已经论证过：这个规模不需要 pgvector。**

3300 个文档 × 1024 维 ≈ 13.5 MB，numpy 暴力余弦是亚毫秒级。为"要做 RAG"去搭向量库，在这个规模上是纯负担。

**3. EXPLAIN 是唯一真正需要真库的东西，而它在 M4 之后才会出现。**

那时再启用 PostgreSQL，且只在该测试目录打 `@pytest.mark.db`。

### 后果

| 项 | 调整 |
|---|---|
| `docker-compose.yml` | 保留，但标注"可选，仅方言/EXPLAIN 验证需要" |
| `ci.yml` 的 pgvector service | 从主测试 job 移除；需要 DB 的用例打 marker 单独跑 |
| `fixtures/sql/bank_fixture.sql` | 需确认在 SQLite 下可执行（去掉 PG 专有类型/语法） |
| `scripts/seed_fixture.py` | 默认建 SQLite 文件 |

### 什么情况下翻案

* 需要验证 Oracle / PostgreSQL 专有方言（`DATE '...'` 字面量、`FETCH FIRST`、`DUAL`）
* 需要 EXPLAIN 预检作为校验的一层
* fixture 数据量超过 SQLite 的便利范围（> 10 万行）

## ADR-0007：多时点对比用「单 SELECT + 分段聚合 + 重复表达式」，M2.1 只做可加总的 delta

**状态**：已接受（2026-11-20，M2.1）
**决策**：

1. 双时点对比在**同一个 SELECT** 内完成：`WHERE etl_dt IN (cur, base)` +
   `SUM(CASE WHEN etl_dt = ? THEN <聚合参数> ELSE 0 END)` 分列聚合。
2. 差值列**重复写两遍完整表达式**，不用 CTE，也不用子查询。
3. 时点条件注入**聚合参数内部**，不套在聚合外面。
4. M2.1 只支持 `delta`，且只接受可加总指标（公式顶层是单个 `SUM`）；越界一律显式报错。

### 背景

`AQ-004` 要"2026年1月末到4月末贷款余额增加额"，输出三列 `cur_balance` /
`base_balance` / `delta`。最自然的写法是：

```sql
SELECT SUM(CASE WHEN etl_dt='2026-04-30' THEN x ELSE 0 END) AS cur_balance,
       SUM(CASE WHEN etl_dt='2026-01-31' THEN x ELSE 0 END) AS base_balance,
       cur_balance - base_balance AS delta        -- ✗ 任何数据库都不合法
FROM ...
```

**SQL 不允许同一个 SELECT 里的表达式引用本层别名**（别名是给 `ORDER BY`
和外层查询用的）。三条出路：

| 方案 | 形状 | 代价 |
|---|---|---|
| **(a) 重复完整表达式** | `SUM(CASE…) - SUM(CASE…)` | SQL 长约 3 倍 |
| (b) CTE | `WITH t AS (SELECT …cur, …base) SELECT cur-base FROM t` | 要先把"CTE 算不算 R-COMP-001 说的子查询"定义清楚 |
| (c) 子查询 | 嵌套 SELECT | 被 `R-COMP-001` 直接排除 |

### 决策理由

**1. 选 (a)：代价是长度，换来规则边界清晰。**

可读性可以用视图/注释补；而"对比查询里藏了一个子查询"这种事，
只有在 review 黄金 SQL 时才看得出来。`R-COMP-001` 的存在理由正是
"不要让人去判断那条子查询算不算违规"。

**2. 时点条件必须注入聚合参数内部，不是套在聚合外面。**

```sql
SUM(CASE WHEN etl_dt='…' THEN x ELSE 0 END)          -- ✓
CASE WHEN etl_dt='…' THEN SUM(x) ELSE 0 END          -- ✗ 语法合法、语义全错
```

后者 SUM 会先在整张表上聚合，再由 CASE 决定要不要 —— **结果只有一行，不报错不告警**。
这条由 `tests/engine/test_compiler_comparison.py::test_point_condition_is_inside_aggregate`
用结构断言钉住（每个 `SUM` 的参数必须是 `CASE`，且没有任何 `CASE` 里装着 `SUM`）。

**3. M2.1 只实现 `delta`，且只接受可加总指标（顶层是单个 `SUM`）。**

分段求和再相加是恒等式，对 `SUM` 成立；对 `AVG` / `COUNT` / 比率不成立
（分段平均再相减没有意义）。所以 `npl_ratio` 这类指标在这里明确报
`DELTA_NOT_ADDITIVE`，而不是产出一条跑得通、口径却错的 SQL。

**4. 越界一律显式报错，不静默降级。** 四个错误码：
`COMPARISON_UNSUPPORTED`（yoy/mom/rate、或 grain=range）、
`COMPARISON_POINT_COUNT`（点数 ≠ 2）、
`MULTI_POINT_WITHOUT_COMPARISON`（两个时点却没说怎么比）、
`DELTA_NOT_ADDITIVE`（指标不可加总）。

### 一个已知的口径缺口（明确接受，不隐瞒）

`ELSE 0` 让缺失时点按 0 参与计算。数学上这是分段求和的正确写法，
**业务上不等于承认"缺失的快照就是零"**：`fixture` 的 D-10 就有 ETL 失败导致某月无快照的场景，
那时 delta 会算成"当前值 - 0"，看起来是大幅增加。

要不要拒答、要不要在答案里标注，属于 L2 门禁与答案披露的职责，
**不在编译器里判断**。这一条已写进 `eval/golden/G-008.sql` 的口径提醒。

### 什么情况下翻案

* 需要 `yoy` / `mom` / `rate`：它们的形状不同（跨年、跨月、除法）。
  若证明"重复表达式"在这些形状下不可维护（例如比率需要 4 份子表达式），
  重开关于 CTE 的讨论 —— 那时也应该是**先扩展 `R-COMP-001` 的定义**，再改形状
* 需要对比**比率/均价**类指标：要么先定义清楚"差值是百分点还是相对变化"，
  要么改用两层结构（CTE）
* SQL 长度成为实际维护负担（例如 4 个时点以上的对比）

## ADR-0008：每月 Top N 用三层查询，月末快照聚合后按月排名

**状态**：已接受（2026-11-23，M2.2）

**决策**：复用 L3 现有聚合构造，再用两个派生表分别做窗口排名和筛选；
使用 `ROW_NUMBER`，按完整月末日期分区、指标降序、主体编号升序，返回每月最多 N 个主体。
不输出内部排名列 `rn`。指标为 NULL 时排在有效值后，多个维度按维度组合排名。

### 方案与理由

* **三层派生表（采用）**：聚合、排名、筛选的别名作用域分明；
  复用现有聚合 AST，外层统一筛 `rn <= N`，不要求方言支持 QUALIFY。
* **两段 CTE**：与 AQ-008 的手写标准答案等价，但此处没有复用中间结果的需求，
  派生表已经足够。黄金集钉住实际编译形状，结果测试验证业务语义。
* **聚合与窗口合在一层**：少一层查询，但窗口排序须重复聚合公式，
  当前优先保留指标投影与排名职责的边界。

### 输入、权限与失败方式

* 使用 `top_n > 0`、`top_n_grain="month"`、非空排名维度，时间为 month/range/month_end。
  支持完整起止闭区间或显式月末列表；区间按日历枚举月末，跨年与闰年由代码处理。
  两种时间写法不能混用，缺时间报 `TIME_UNRESOLVED`。
* 只读取月末快照，防止累加月中记录；缺失月份不回退、不补零。
  没有月末的区间产出恒假时间条件，仍保留业务与权限条件。
* 业务、行级权限条件复用原有注入点，必须在聚合与排名之前生效；
  无权限取值的策略仍生成 `1 = 0`，不允许排名之后再过滤权限。
* 全局 Top N、comparison 混用、report/union 分支均显式拒绝；
  非整数/非正 N、缺排名维度、非法时间、输出重名均有稳定错误码。
  加载器拒绝小数与布尔 N，避免静默截断或转换。

### 验收与翻案条件

验收包括手写 `G-010.sql`、窗口结构断言、SQLite 内存结果测试以及错误边界测试。
结果测试覆盖跨月不同赢家、并列、同主体多笔记录、名称漂移、月中快照、缺失月份、
过滤与权限、跨年、闰年、多维度和 NULL 指标；黄金集将 Intent 传给 L4，
反例保证缺窗口时会失败。L4 保持独立，从 SQL 文本重新解析。

若业务需要“并列全保留”（RANK/DENSE_RANK）、每月按另一个维度再分区、
非月末日频数据，或报表分支排名，先扩展 Intent/语义元数据和验收口径，再扩展编译形状。

## ADR-0009：先做显式、安全的双表关联，不自动规划多跳路径

**状态**：已接受（2026-11-23，M2.3；用户确认方案三）。

### 决策与理由

采用受限双表编译，而非只拼 JOIN 节点或直接建设通用规划器。
`LevelDef.table` 明确来源（默认主表以保持兼容），`RelationDef.cardinality` 默认 unknown，
只接受有效方向为 many_to_one/one_to_one 的 INNER/LEFT。
枚举全部候选关系：缺失、重复、歧义均拒绝；INNER 可以反转关系和基数，LEFT 不自动反转保留侧。
最多两表，主表不随权限或关系排列顺序改变；先限定事实表度量 + 维表维度/过滤。
本轮不组合双表与 delta/Top N/report/union，不做关联表度量、复合键、自关联或预聚合。

这样能把“依赖解析 → 关系检查 → 字段绑定 → 装配”分开，未来依据真实多跳用例扩展，
而不是现在引入路径打分和通用图算法。Intent 不增加 SQL 字段，模型调用次数不变。

### 权限与数据质量

全部参与表检查 Scope，所有实际物理列检查白名单（包括 JOIN/权限列）；
未配置表白名单不限制，显式空集合拒绝，通配符指标不能绕过显式列限制。
单表与 JOIN 使用同一 Scope 契约：None 不限制、显式空 Scope 拒绝；L4 的旧空 Scope 放行测试相应改成拒绝断言。

权限按表绑定且保留声明顺序；不为应用无关表策略而自动加入表。
ON 只放关系等值键，WHERE 顺序为时间 → 业务 → 权限。
LEFT 无右表限制时保留未匹配主表行；有右表业务过滤/权限时排除未匹配或无权记录。
空权限必须使整个结果为空，不把无权金额重新累计到 NULL 分组。

编译器不读库，基数声明不是实际数据唯一性验证。
SQLite 结果测试使用主键保证维表键唯一；独立无约束反例说明重复键确实放大金额，
不将该反例谎称为编译器自动检测。生产侧需唯一约束或独立数据检查。

### 黄金集与验收

G-011~G-014 钉住 INNER、LEFT、双表过滤与权限、LEFT 空权限形状。
为对照同一表关系的配置，黄金清单增加可选 relations（L0），省略沿用目录、空列表显式无关系，
逐项严格验证后仅对当前用例不可变替换，不让 Intent 选择 SQL 语法。
配置错误、覆盖失效、共用目录被污染均有反例验证。

AQ-007 维持单表核销语义，不能拿它冒充 JOIN 正例。
新 JOIN 单测 92 项包含 SQLite 实际执行；全量 398 项、黄金集 14/14 通过。
修正混用占位符/裸列的公式绑定，并拒绝 FROM/WHERE/多语句等非表达式公式。

### 何时重新讨论

真实需求需要三表、多跳、桥接、事实表对事实表、有效期维度、联合键，或 JOIN 与对比/排名组合时，
先增加业务用例、基数与权限规则，再扩语义配置及确定性解析器。
不会因超出当前范围就默默丢掉来源、维度或条件，或交给模型自由拼 JOIN。

## ADR-0010：用独立报表定义读取预计算结果，按显式月份 UNION ALL

**状态**：已接受并实现（2026-11-23，M2.4；用户确认书面设计）。

### 决策与理由

不硬编码产品报表，也不自动扫描表家族。新增独立 `ReportDef`，由 `SemanticCatalog.reports`
按业务 metric_code 登记值列、月份列、固定维度绑定和 YYYYMM → 物理表白名单。
明细的指标公式/source_tables/维度默认列不变，报表不借临时替换目录来复用明细编译。

解析指标后即按 report/union 分流；两种模式均由实际去重月份数决定 Select 或 Union，
所有月份预先解析，不能缺月时跳过、猜表或回退明细。只消费结构化整月时间，不扩展 L1。
逐分支直接投影月份、维度和预计算值，最终 UNION ALL 排序；不把比例 SUM/AVG/MAX，不乘 100。
维度集合必须等于报表固定粒度，即使已过滤也不能丢维度；不与 JOIN/对比/Top N 混用。

### 权限和独立校验

每张实际分表检查表权限、所有引用列和本表行策略；不要求未读取的底层明细表权限。
None Scope 不限制，显式空 Scope 拒绝；任何表/列拒绝整条失败。
未使用表的行策略不引入来源，空值策略保留该分支的 1=0，而非删掉月份或过滤其他合法分支。
这不叫部分吞错：月份、来源、表列权限均完整通过，行级结果本就可以为空。

复用单表 SourcePlan 字段接口，但不走 JOIN 规划器和明细两表上限。
别名按 t1/t1_2/t1_3 唯一分配；每个分支检查 FROM，根为 Union 时不要求 FROM。
compile_intent 返回类型拓宽为 exp.Query；L4 仍只接收最终 SQL 文本及独立目录/权限/意图。
用早期分表缺列、后期分表有列的反例确认列目录不会因别名复用而掩盖错误。

### 数据责任与验收

口径与唯一粒度是知识契约，需要源表 PK 或外部数据检查保障，编译器不读库验证。
标准产品报表与逾期口径报表均存在于独立名字目录；不能靠 UNKNOWN_TABLE 来假装业务隔离完成。
SQLite 验证标准 LP03 为 0.140700，而非逾期值 0.128300；零、NULL、重复原值不被汇总或填补。
AQ-006 原答案 MAX/GROUP BY 在 PK 前提下与直接投影业务等价，不修改原评测语义、不冒称文本相同。

手写 G-015~G-018，G-001~G-014 保持原 SQL；562 项测试、18/18 黄金用例通过。
旧负例现在先经过真实报表路由，错误由通用 JOIN/Top N 未支持改为报表来源缺失/形状不支持。
本轮没有模型调用、网络或外部数据库；三方言只验证文本渲染和回解析。

### 何时重新讨论

真实需求需要不同粒度再聚合、可加总报表、多指标、报表 JOIN、自动表家族、日粒度或报表排名时，
先补粒度/聚合性/单位/来源及权限规则和业务正反例，再扩定义与编译器；不默默改变已存比例语义。
下一步 M2.5 的占比需单独设计整体分母，不能拿跨月报表求平均代替。
