# M2.3：受限双表关联编译设计

日期：2026-11-23

状态：用户已于 2026-11-23 确认；实现与验收完成，398 项测试及 14 条黄金用例通过。

## 1. 目标与已有决策

在现有 `Intent + SemanticCatalog + Scope → AST → SQL` 编译链中，支持有明确配置的双表关联。
不引入模型调用、数据库连接、自然语言推断或自动选路；编译失败不重试。

用户已了解并选择“受限双表关联编译”，而非“只补 JOIN 节点”或“通用关联规划器”。
未来可以演进到通用规划，但本轮不预建多跳搜索、路径打分和通用聚合重写框架。

本轮交付目标是：事实表提供指标，关联的唯一维表提供分组、展示或过滤字段。
典型问题是“2026 年 4 月末，各上级机构贷款余额是多少”。

## 2. 当前代码与需要解决的缺口

- `MetricDef.source_tables` 可列多表，但 `_primary_table` 只取第一张，不能继续静默忽略其他来源。
- `RelationDef` 已有左右表、左右列和 INNER/LEFT/RIGHT 类型，没有基数声明。
- `SemanticCatalog.relation_between` 返回第一个匹配关系，不能据此判断关系是否有歧义。
- `LevelDef` 只有 `group_by/display`，没有来源表；维度与过滤默认绑定主表。
- 指标公式支持主表占位符；已有列别名处理不能直接承担完整双表绑定。
- 行级策略有 `table`，但 `build_policy_conditions` 目前把全部策略绑定到一个别名。
- `Scope.columns` 已建模但编译器尚未执行列白名单；新增 JOIN 不应继续放大这一权限缺口。
- 黄金集门禁已独立校验 SQL 文本，不能改成复用编译器计划来证明正确。

路线图中的 AQ-007 不是 JOIN 正例：其标准答案只查核销表，且明确警告不必要关联会放大金额。
本轮不改写 AQ-007 的语义，也不宣称通过 JOIN 实现了核销指标或业务日期查询。

## 3. 支持范围

### 3.1 支持

- 一张主事实表、至多一张维表，一条明确的等值关联。
- 由指标来源表与本次使用的维度、有效业务过滤字段的来源表确定实际依赖。
- 主表固定为指标来源的第一张表；不会因 Scope、关系排列顺序或模型输出切换主表。
- INNER JOIN 与以主表为保留侧的 LEFT JOIN。
- 从主表出发为 many_to_one 或 one_to_one 的关系。
- 主表指标聚合，关联表维度分组、名称展示和业务过滤。
- 单表查询保持原有 SQL 形状；已有单表 delta、每月 Top N 不回归。

### 3.2 显式拒绝

- 三张及以上表、多跳、桥接表、自关联和多条候选关系自动选择。
- RIGHT/FULL/CROSS JOIN、非等值关联、复合键、有效期关联。
- 从主表出发的一对多、多对多和未声明基数的双表关系。
- 将反向配置的 LEFT JOIN 自动转换成其他保留方向。
- 关联表提供度量的跨表公式：即使维表键唯一，也可能因事实记录数重复汇总维表度量。
- 本轮双表 JOIN 与 delta 或每月 Top N 的组合；这类请求显式拒绝，单表能力不受影响。
- report/union 分支的 JOIN；继续遵守现有禁 JOIN 规则。

上述限制是可解释的能力边界，不能回退到只查主表，也不能丢弃维度或过滤后继续执行。

## 4. 语义配置

### 4.1 维度来源

为 `LevelDef` 增加可选 `table`，默认空值表示主表，以兼容全部现有维度定义。
`group_by` 和 `display` 均来自该表，字段名保持为列名，不把任意 SQL 塞进配置。
本轮不允许一个 level 的编号与名称分别来自不同表。

新增“上级机构”维度：来源 `dim_org`，分组列 `parent_org_no`，不配置上级名称。
获取上级名称需要再次关联机构表，不属于本轮双表范围。

现有“机构”和“产品”维度仍从贷款明细取值，不因为目录中出现 `dim_org` 就自动改变口径。

### 4.2 关系基数与方向

为 `RelationDef` 增加 `cardinality`，相对声明的 left → right：
`unknown / one_to_one / many_to_one / one_to_many / many_to_many`，默认 `unknown`。

编译时须先枚举连接这两张表的全部关系，零条拒绝，多条拒绝，包括内容重复的声明。
不能沿用“取第一条”的行为掩盖配置歧义。

INNER 可按主表方向规范化关系，同时反转基数判断：
声明为一对多但主表在声明右侧时，实际方向是多对一，可以接受。
LEFT 必须声明左表就是主表；反向配置拒绝，不擅自改写其保留侧。

演示关系为：贷款明细 `org_no` → `dim_org.org_no`，many_to_one。

### 4.3 基数声明不等于数据验证

编译器只读配置，不读数据库，不能在编译期发现真实数据中的重复维表键。
演示及结果测试的 `dim_org.org_no` 使用主键；重复键插入由 SQLite 约束拒绝。

单测验证配置中未知或不安全基数会失败；另用独立反例展示无唯一约束时 JOIN 会放大金额。
不得将该反例描述为编译器能自动检测数据重复。

实际接入要求维表关联键具有可信唯一约束或经过独立数据质量验证。
不使用 DISTINCT、任意 MAX 或自动去重掩盖配置与数据质量问题。

## 5. 编译模块与数据流

新增小型、确定性的关联解析模块，返回本次查询的主表、可选第二张表、别名映射与已校验关联。
它只是单步关系解析，不是通用图规划器。

1. 解析指标，解析分组与过滤维度的实际 level。
2. 收集来源表并去重，保持确定顺序；超过两表立即失败。
3. 查找唯一关系，校验类型、方向、基数与本次 Intent 的形状组合。
4. 检查全部实际使用表的 Scope，建立表 → 别名映射。
5. 构造时间、业务过滤、权限条件，按所属表绑定字段。
6. 复用指标与维度投影构造，装配 FROM/JOIN/WHERE/GROUP BY。
7. 校验本次使用的物理列是否被 Scope 列白名单允许，完成结构自检和渲染。
8. L4 从 SQL 文本重新解析，独立检查表列名称、表范围与业务规则。

默认别名沿用主表 `t1`、关联表 `t2`；自定义主表 alias 时也必须生成不冲突的关联表别名。
表身份按明确配置匹配，大小写规范化；不能通过剥离 schema 猜测同名表。

模块边界：关联解析负责依赖、方向和绑定；指标负责公式；conditions 负责业务与权限条件；
顶层编译器负责装配。只做为本功能必要的接口调整，不进行无关重构。

## 6. 指标、时间、维度与过滤

- `{tbl}`、`{t}` 和未限定列仍代表主表度量；混合占位符与未限定列时也要完整绑定。
- 双表公式中显式的主表物理限定名可规范化为主表别名；不得引用未声明表或关联表度量。
- 双表路径的非法限定名必须报错，不能把未知别名留给数据库碰运气。
- 时间继续由 `ValidationPolicy.snapshot_column` 指向主表，不给维表自动加快照条件。
- 维度从 `level.table` 获取别名；编号分组，名称只做 MAX。
- 业务过滤从同一个 level 获取表与列，继续复用精确码值转换。
- 关联维度即使只用于过滤、未出现在 dimensions 中，也必须引入正确的关联。
- Filter.value 为 None 的条目不构造谓词，不应因此额外关联一张表。
- 涉及的新过滤路径明确支持 eq/in；其他运算符若本轮未实现，必须显式拒绝，不能降级成 eq。
- 双表输出列别名重复时拒绝，避免外层调用者无法区分两列。

## 7. 权限与 LEFT JOIN 语义

### 7.1 表与列

主表和关联表都必须在 Scope 范围内；未提供 Scope 沿用现有无限制调用约定。
显式提供但不包含任何可见表的 Scope 必须拒绝，不能因其布尔值为假而跳过检查。

`Scope.columns` 中未配置的表保持“不限制列”；显式空集合表示该表一列不可见。
本次 SQL 使用的指标、时间、分组、名称、业务过滤、JOIN 键和权限条件所引用的物理列均受检查。
只有因权限配置产生的内部 `1 = 0` 等字面量条件不涉及列权限。
复用这条确定性检查覆盖已有单表路径，以保持同一 Scope 契约。

### 7.2 行级策略

根据 `RowPolicy.table` 定位实际使用表的别名；策略不允许串到另一张表。
Scope 中对本次未使用表的策略不生成 SQL，也不为了应用这些策略额外关联表。
本次参与表的空取值策略仍生成 WHERE `1 = 0`，整个结果为空。

### 7.3 条件位置

JOIN ON 只描述关系等值键；时间、用户业务过滤、行级权限放 WHERE。
WHERE 合成顺序保持“时间 → 业务 → 权限”，权限按原策略声明顺序生成。

LEFT 无右表过滤/权限条件时保留未匹配主表行，维度键为 NULL。
若用户筛选右表字段，未匹配行自然不满足筛选，被排除。
若存在右表行级策略，右侧未匹配或无权的行也被排除，这是明确的安全语义。
不能把权限只移入 ON，让无权关联变成 NULL 分组并继续累计主表金额。

这里的 LEFT 保留语义仅针对关联本身，不覆盖之后明确施加的业务过滤与访问限制。

## 8. 稳定错误分类

沿用 CompileError 的 stage/code，不用宽泛异常或静默降级表达边界。

| 条件 | stage | code |
|---|---|---|
| 两表无关系 | symbol_table | JOIN_RELATION_MISSING |
| 两表有多条关系 | type_check | JOIN_RELATION_AMBIGUOUS |
| 超过两表 | type_check | JOIN_TABLE_LIMIT |
| 不支持的关联类型或方向 | type_check | JOIN_TYPE_UNSUPPORTED |
| 未声明或不安全的有效基数 | type_check | JOIN_CARDINALITY_UNSAFE |
| JOIN 与 delta/Top N/report/union 混用 | intent | JOIN_SHAPE_UNSUPPORTED |
| 未声明限定名或关联表度量公式 | type_check | JOIN_FORMULA_UNSUPPORTED |
| 双表过滤运算符未支持 | intent | JOIN_FILTER_UNSUPPORTED |
| 双表投影重名 | type_check | JOIN_OUTPUT_COLLISION |
| 参与表越权 | scope | METRIC_OUT_OF_SCOPE（主表）/ TABLE_NOT_IN_SCOPE（关联表） |
| 物理列越权 | scope | COLUMN_NOT_IN_SCOPE |

已有指标、维度、码值、时间错误沿用原错误码，不重复创造同义错误。

## 9. 验收用例

### 9.1 手写黄金 SQL

新增 G-011 起的独立用例，至少覆盖：

1. INNER：按 `dim_org.parent_org_no` 汇总贷款余额。
2. LEFT：包含机构维表中找不到的贷款机构，并保留 NULL 上级分组。
3. 关联表业务过滤及两表行级权限的联合形状。

每条都有 covers/why_hard，覆盖 R-TBL-001、R-NAME-001 及适用业务规则。
不能由编译器输出自动生成或 bless 黄金 SQL。

在假语义层增加 `dim_org`、上级机构维度及关系，在独立的名字目录增加对应列。
原有维度语义和 G-001~G-010 SQL 不应因新增关系改变。
JOIN 正例不硬绑定 AQ-007；修正 ROADMAP 对该用例的错误对应。

### 9.2 AST 和 SQLite 内存结果

- 多笔贷款映射到同一机构时，余额按预期汇总且不重复。
- INNER 排除无匹配机构；LEFT 保留无匹配机构及 NULL 维度分组。
- 维表键重复被测试库唯一约束拒绝；独立反例揭示无约束时的金额放大。
- 编号和名称同名、不同表同名列时，全部引用绑定正确表别名。
- 名称只做 MAX，不进 GROUP BY；多维度组合保持含义。
- 仅过滤关联维度即可触发 JOIN，None 过滤不触发无效关联。
- 两张表的行级策略分别生效；空策略取值、右表不可访问、空 Scope 均失败关闭。
- 右表权限不能将无权余额重新计入 LEFT 的 NULL 分组。
- 列白名单覆盖 JOIN 键、时间、指标和维度；显式空白名单与未配置可区分。
- 关系声明顺序、双向 INNER 规范化、自定义别名、合法 schema 限定保持确定性。
- 未知关系、歧义、不安全基数、三表、反向 LEFT、不支持类型和混合形状均报稳定错误。
- 原有单表、delta、Top N、黄金集与校验器单测全部回归。

使用本地虚拟环境执行 pytest、scripts.check_golden、ruff check、变更文件的 ruff format --check，
并执行 git diff --check。测试不调用模型，不连接外部数据库，不访问网络。

## 10. 后续演进到方案二的接缝

保留“解析依赖 → 解析关系 → 绑定字段 → 装配 SQL”的边界。
未来有真实三表需求时，可以扩展关系解析而不让 Intent 接受 SQL 或让模型选 JOIN 条件。

演进顺序是：补真实多跳用例 → 明确路径歧义和基数规则 → 扩展语义配置与失败分类 → 扩展规划。
事实表对事实表关联、预聚合、复合键和路径选择分别验证，不因需要方案二就一次性引入。
本次不保证任何三表查询，不以代码预留数量衡量“可扩展性”。
