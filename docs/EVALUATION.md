# 评测规范

本文件定义 wenshu 的测试与评测口径。目标是让“准确率”“通过率”“已验证”这些词有明确含义，避免把离线回放的通过率误当成真实模型能力。

## 1. 测试与评测的区别

- **测试**：验证某个函数、模块或契约在特定输入下是否按预期工作。
- **评测**：在一组有代表性的问题上，衡量系统整体表现，并给出可比较的指标。
- **黄金集**：人工编写的标准 SQL，用于判断编译器产物是否符合预期形状。
- **回放**：用固定 cassette 代替真实模型，验证契约和确定性。
- **真实模型评测**：现场调用模型，衡量理解、澄清、编译和执行的端到端表现。

测试通过不等于评测通过；离线评测通过不等于真实模型可用。

## 2. 评测层次

| 层次 | 验证什么 | 是否需要模型 | 是否需要数据库 |
|---|---|---|---|
| 单元测试 | 函数、数据结构、错误码 | 通常不需要 | 通常不需要 |
| 契约测试 | 抽取/澄清的输入输出契约 | fake/replay | 不需要 |
| 黄金集 | 编译产物与手写 SQL 的结构等价 | 不需要 | 不需要 |
| 结果集测试 | SQL 在 SQLite 上的实际计算结果 | 不需要 | SQLite |
| 端到端 | 问题到 rows 的完整链路 | replay | SQLite |
| 真实模型评测 | 真实模型理解与端到端准确率 | real | 视场景而定 |

## 3. 黄金集纪律

- 黄金 SQL 必须人工编写和评审。
- 不提供“一键用引擎产出刷新黄金 SQL”的命令。
- 测试失败时修实现，不修改黄金答案。
- 新增黄金用例必须说明覆盖的形状、口径陷阱和失败方式。
- `expected_compile_error` 用于预期编译拒绝的用例，不能伪造可执行 SQL。
- 黄金 SQL、评测集和 cassette 是不同资产，不能混用。
- 任何黄金答案变更都必须在提交信息中单独说明并给出业务理由。

## 4. 离线评测

运行：

```powershell
uv run python -m scripts.evaluate
```

默认覆盖：

- Intent 抽取。
- 澄清。
- 黄金 SQL。
- 本地 SQLite 端到端样本。

输出：

```text
eval/report.json
eval/report.md
```

两个文件都是机器产物，不提交；每次运行都会重新生成并带耗时，最新数字只记录在 `docs/CONTEXT.md`。

报告必须明确：

- 模型模式是 `replay`。
- 未使用真实模型。
- 未使用外部数据库。
- 每个套件的通过数、失败数、模型调用数和耗时。
- 失败样本的阶段、错误码和说明。

离线评测的 100% 只表示固定回放样本符合手写预期，不表示任意自然语言问题的真实准确率。

## 5. 指标定义

### 5.1 理解层

- Intent 字段准确率：指标、时间、维度、过滤、对比等字段是否与人工预期一致。
- 结构合法率：模型输出是否通过 schema、日期和字段白名单校验。
- 未知概念误识别率：模型是否把不存在的指标或维度映射成已有概念。
- 澄清状态准确率：`needs_clarification` / `slots_complete` 是否符合预期。
- 模型调用次数：每个问题实际调用了多少次模型。

### 5.2 编译层

- 编译成功率：能从 Intent 产出 SQL 的比例。
- 黄金结构一致率：编译产物与手写黄金 SQL 结构等价的比例。
- 校验通过率：SQL 通过 L4 的比例。
- 错误码分布：失败发生在哪个 stage 和 code。

### 5.3 执行层

- 结果准确率：返回 rows 与人工结果集一致的比例。
- 行数截断率：是否触发返回上限。
- 超时率：是否触发查询预算。
- 只读违例率：是否出现写操作或危险操作。
- 权限越界率：是否返回 Scope 之外的数据。

### 5.4 系统层

- 端到端通过率：从问题到正确结果的比例。
- 拒答准确率：不可答/无权限的问题是否正确拒绝。
- P50/P95 延迟。
- 模型调用成本。
- 路由准确率：引入双路由后，是否选择了预期执行路径。

## 6. 真实模型评测

当前状态：round 1 基线 run_id `20261127T064047Z-e239b55`（2026-11-27）；2026-11-28 用 `intent-extraction-v7` 复测两次全对（run `20261128T054726Z-4d3ea6e`、`20261128T054855Z-4d3ea6e`）。结果与归因见 `docs/CONTEXT.md`；30 条规范问法、单模型单版本，且题集参与了提示词迭代，不能当作真实用户准确率。

运行方式（人工步骤，需要密钥，不在 CI）：

```powershell
$env:WENSHU_LLM_MODE = 'real'
$env:WENSHU_LLM_BASE_URL = 'https://api.deepseek.com/v1'
$env:WENSHU_LLM_MODEL = 'deepseek-flash'
$env:WENSHU_LLM_API_KEY = Read-Host 'DeepSeek API Key'
$env:WENSHU_LLM_THINKING = 'disabled'
uv run python -m scripts.evaluate_real --case EX-001 --repeats 1   # 冒烟
uv run python -m scripts.evaluate_real                            # 全量
```

- `--repeats` 默认 3；`--case` 可重复，用于冒烟；`--max-calls` 默认 200。
- 前置条件：模式为 `real`、密钥非空、思考模式为 `disabled`、输出目录不存在；否则退出码 2，不发起调用。
- 输出写到 `eval/real/<run_id>/`：`report.json`、`report.md`、`calls.jsonl`、`review.md`。该目录已忽略，**任何一次运行的产物都不提交**；原始输出只留在运行它的电脑。
- 退出码：0 全部通过；1 有失败或未完成；2 前置检查失败；3 预算用完或连续 `transport` 失败中止。
- 运行结束后把 run_id、所在电脑、两套指标、不稳定题和归因结论写回 `docs/CONTEXT.md`，措辞遵守第 9 节。

进行时必须遵守：

1. 明确模型名称、版本、温度、超时、prompt 版本和数据集版本。
2. 使用固定问题集和固定验收标准。
3. 保存原始模型输出、解析后的 Intent、编译 SQL、校验结果和执行结果。
4. 不把敏感数据发送到公共模型；使用私有部署或脱敏数据。
5. 不自动刷新黄金答案或评测预期。
6. 失败样本必须人工归因，不能只看总数。
7. 报告必须区分“模型理解错误”“编译错误”“校验错误”“执行错误”“评测数据错误”。
8. 未完成真实模型评测前，不得声称真实准确率或生产可用。

### 6.1 round 1 与后续轮次的比较边界

- round 1 的 run_id `20261127T064047Z-e239b55`、原始产物与当时口径下的汇总数字保持不变，不覆盖或追溯改写。

- 直接跨轮比较不包含 EX-004（预期变化）、AQ-006/AQ-008（题面变化）和 AQ-007（排除）。可比子集为 19 条抽取、7 条执行，两个套件分别汇总。
- 完整轮次指标与可比子集指标分开说明，记录代码版本、题集 SHA256、prompt 版本及比较范围；沿用既有评分算法和第 7 节的 transport/未完成口径，不修改运行器重算旧报告。
- 修正后的 EX-004 仍参加 round 2，不标为 excluded；预计 20 条抽取 + 9 条执行，各 3 次，共 87 次正式调用。排除跨轮比较不等于排除当轮测量。
- 当前真实运行状态只见 `docs/CONTEXT.md`；修正离线预期不代表已运行 round 2 或真实模型准确率提升。
- unresolved 片段判定（2026-11-28 起）：错误码一致且片段逐一对应；模型片段允许比预期多出至多 4 个字的边界词（如“按管户口径”对“管户口径”），片段数量必须一致，整句塞入不得通过。旧轮次按当时的精确比对口径记录，不追溯重算。

### 6.2 盲测集

- 盲测集是**未参与提示词迭代**的抽取题，放 `eval/blind/blind_extraction_v1.yaml`，结构与回归抽取题相同（无 cassette）。不进 `tests/fixtures`、不进 CI、不配 cassette。
- 运行前写死；运行后不改题、不改预期、不因结果调提示词。结果无论多少都写进 `docs/CONTEXT.md`。
- 预期按业务含义写；策略类条目沿用现行契约并在 `why_hard` 注明，便于把“契约 vs 常识”的失败和真缺口分开。
- 运行：`uv run python -m scripts.evaluate_real --extraction-cases eval/blind/blind_extraction_v1.yaml --case BL-001 ...`；报告 metadata 记录 `extraction_cases_path` 与 sha256。
- 盲测集一旦被用来改提示词，就不再是盲测；下一轮要换新题。
- 当前结果：v1 / 38 题 / 提示词 v7：全对 89.5%，零不稳定（run `20261128T061407Z-e3e8468`）。

## 7. 失败归因

每条失败至少记录：

```text
sample_id
stage: understanding | clarification | semantic | scope | compiler | validation | execution | data | transport
code
message
expected
actual
```

`transport` 指超时、网络错误或非 2xx 响应；它单独归因，**不计入准确率分母**，受影响题标记为未完成。

归因表比单一准确率更重要。它决定下一步应该改 prompt、语义层、编译器、校验器还是数据。

## 8. 新增评测用例

新增用例必须回答：

- 它覆盖哪个业务形状或口径陷阱？
- 为什么现有用例覆盖不了？
- 预期 Intent、SQL 或结果是什么？
- 失败时应该落在哪个 stage/code？
- 是否需要真实模型或外部数据库？
- 是否包含必要的负例？

评测集不能只加“能答”的样本，也要包含：

- 指标不存在。
- 维度不存在。
- 机构值未登记。
- 权限不足。
- 时间缺失或歧义。
- 不支持的 SQL 形状。
- 空结果和零分母。

无法公平测量的用例（语义层缺口、题面与 prompt 冲突）必须用 `measurement.status: excluded` 标记并写明原因；
运行器单列排除题，不进入准确率分母，也不得静默跳过或计入模型失败。

## 9. 结论边界

当前可以说：

- 离线契约、黄金 SQL 和固定端到端样本通过。
- 编译器在已覆盖形状上行为确定。
- 校验器与编译器独立。
- SQLite 只读执行和权限过滤已验证。

当前不能说：

- 真实模型准确率已达标。
- 任意自然语言问题都能正确出数。
- 已连接真实业务数据库。
- 已验证 Oracle/PostgreSQL 生产方言。
- 双路由或 ReAct 能提高准确率。
